## ISS-001: Model artifact format is implicit during training and inference
- **Status:** Open
- **Type:** bug · **Area:** training, inference · **Priority:** P1
- **Plan:** — (Phase 1, task A3 in `.plan/parallel_agent_setup.md`)
- **Impact:** A trained XGBoost run can publish `model.json` as its primary `artifact_uri`. Batch inference treats every non-ZIP model artifact as joblib data, so loading that URI with `joblib.load()` fails with `KeyError: 123`.
- **Root cause:** The XGBoost trainer writes both `model.joblib` and native `model.json`. The training executor uploads both, but the primary artifact was selected by filesystem iteration order. Inference then infers the loader from ZIP-vs-non-ZIP rather than from explicit artifact metadata.
- **Temporary workaround:** Prefer `model.joblib` over `model.json` when selecting the primary artifact for new training runs. Existing model versions whose `artifact_uri` points to `model.json` are not changed by this workaround.
- **Long-term direction:** Make the artifact format/loader explicit in persisted model metadata or a manifest. Have inference dispatch to the appropriate loader (for example, joblib or XGBoost's native JSON loader) based on that declaration, and retain a deliberate compatibility path for existing model versions. Define and test the primary-artifact contract independently of filesystem ordering.
- **Additional findings [26-11-14]:** Training picks the primary file by a fixed extension list (`usfds-core/src/usfds_core/services/training/executor.py:113-128`); inference dispatches on extension only (`inference_service.py:155-160`, `inference/executor.py:588-598`), so `.pt` / `.onnx` / `.json` artifacts also fail. Framework is guessed from the model name (`training/executor.py:199`).
