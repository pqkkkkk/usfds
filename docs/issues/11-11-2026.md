## ISS-004: Double-transfer overhead from temporary `uploads/` staging during Presigned URL ingestion
- **Status:** Open
- **Type:** improvement · **Area:** storage, data-management, inference, training · **Priority:** P3
- **Plan:** — (Phase 2; do after ISS-001 and ISS-003)
- **Impact:** In Client-Server mode, uploading data via S3 Presigned URLs causes redundant network/storage I/O, extra API server memory usage, and increased request latency. Files are uploaded once by the client to `uploads/...`, then read/downloaded by the API server, copied or re-uploaded to their canonical prefix (`datasets/...`, `datasets/{project_id}/inferences/inputs/...`, or `models/{model_id}/plugin_source.zip`), and finally deleted from `uploads/...`.
- **Root cause:**
  - `storage_router.py` generates presigned `PUT` URLs under a temporary staging key `uploads/{purpose}/{scope}/{uuid4()}/{filename}` because final domain IDs (`dataset_id`, `job_id`, `model_id`) are generated inside `usfds-core` services only after payload submission.
  - `InferenceService._resolve_input_source` reads the entire uploaded object into memory via `file_storage.read_bytes()`, validates it with Pandas, re-uploads the exact same bytes to `datasets/{project_id}/inferences/inputs/{job_id}/{filename}` via `file_storage.save_bytes()`, and deletes the temporary key.
  - `DatasetIngestionService.import_dataset` performs validation, copies the object to `datasets/{dataset_id}/raw/{filename}` via `file_storage.save_file()` (server-side `copy_object` on S3), and deletes the temporary key.
  - `TrainingOrchestrationService.register_plugged_model` downloads the uploaded `.zip` via `read_bytes()`, deletes the temporary key, validates/re-packages the plugin, and uploads `models/{model_id}/plugin_source.zip`.
- **Temporary workaround:** Keep the `uploads/` staging prefix and immediately delete temporary objects inside `DatasetIngestionService.import_dataset`, `InferenceService._resolve_input_source`, and `TrainingOrchestrationService.register_plugged_model` after reading/copying so orphaned duplicates do not accumulate on S3/RustFS.
- **Long-term direction:**
  - Pre-allocate canonical IDs or upload directly to the canonical destination key where possible, or pass pre-allocated job/dataset metadata so the client uploads once to the final key without a staging copy/re-upload cycle.
  - For `InferenceService._resolve_input_source`, use `file_storage.save_file()` (server-side `copy_object`) or a streaming/header-only validation path rather than `read_bytes()` + `save_bytes()` when storing the input snapshot, and configure S3 bucket Lifecycle Expiration rules on `uploads/` as a safety net for aborted client uploads.
- **Additional findings [26-11-14]:** The `uploads/` prefix check is copy-pasted in 3 places (`ingestion.py:174`, `training_service.py:272`, `inference_service.py:623`). In plugin registration the staging object is deleted *before* `register_from_zip` validates it, so a failed validation leaves no copy for retry.
